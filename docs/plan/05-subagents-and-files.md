## Claude and Codex subagent trees

1. Index every discovered Lane under its provider session. For Claude, the agent filename supplies the agent key, the containing folder supplies the root, and the Agent tool call may live in the main transcript or another child's transcript. Read only the metadata needed to display type, description, model, effort and outcome. Index root and child <code>tool_use.id</code> values, then match <code>meta.toolUseId</code> to the unique spawning call. Cross-check <code>toolUseResult.agentId</code> when present. Use <code>spawnDepth</code> as a consistency check.
2. Create a pending row for a spawning call that precedes its transcript. For a transcript without a unique spawn match, show it beneath the root in the Agent map with a missing-parent label. Reconcile metadata arriving before or after either log. Protect against cycles, file replacements, repeated IDs, and cross-project mismatches. Never use simultaneous activity as proof of ancestry.
3. For Codex, use <code>session_meta.parent_thread_id</code> and the explicit relation under <code>source.subagent.thread_spawn</code>. Corroborate with <code>SubAgentActivity.agent_thread_id</code> and child metadata. Resolve late rollouts in the same tree. Show observed agent-to-agent messages from provider-specific records with role labels.
4. Expose an activity summary per lane with the latest trustworthy action and timestamp. A collapsed lane can capture a command running, file edit, or completed task without requiring a full transcript. A lane remains inspectable if the parent has ended.

## Link Claude Bash tasks to Codex

The first half of the link exists in local data. In 35 sampled main transcripts there were 27 recognizable Codex Bash invocations, 24 marked background. For 22 corresponding results a task reference matched a local task file. In the first 512 KiB of each of 251 available <code>.output</code> files, 13 contained generic session-ID-like text, with no match in the current Codex rollout inventory. The read-only review of <code>~/.claude/skills/codex-first</code> found that the fresh launch example suppresses stderr and the resume script redirects both streams to an attempt log. The marker convention makes the identity visible in the Claude task output while preserving that workflow.

1. Identify a genuine Claude <code>Bash</code> tool call with a recognizable <code>codex exec</code> or <code>codex exec resume</code> invocation in its recorded command. Use syntax-aware conservative extraction for shell wrappers if needed. The parser treats the command as data. Never run a shell to interpret the log, evaluate substitutions, or read an arbitrary redirected prompt/output path.
2. Use its paired result's <code>toolUseResult.backgroundTaskId</code>, a matching structured task notification, or an allowlisted reference to a file with exactly that task basename in the same Claude session's task directory. Record the owning lane and Bash call ID. Corroborate the task ID and session in the resolved Windows path. A task in a child lane belongs under that child.
3. Read a bounded prefix from the approved task file or the paired Bash result's known output fields. Accept an exact launcher marker line <code>AGENT_LENS_CODEX_SESSION=&lt;UUID&gt;</code>, a structured <code>thread.started.thread_id</code> start event when the launcher uses <code>--json</code>, or a strict native CLI startup header with <code>session id: &lt;UUID&gt;</code>. Require a canonical matching rollout in an approved Codex profile home and corroborate the launch interval and recorded cwd. The Claude task association supplies the parent. An arbitrary UUID in output supplies no identity evidence.
4. For <code>codex exec resume</code>, an exact UUID argument can be evidence if the command shape is unambiguous, the candidate thread exists, and a new turn aligns with the task interval and repo. Only link that resume turn. For new runs, repo/cwd, chronology, and recognizable CLI source are corroboration only. Conflicting headers, multiple candidate turns, or missing corroboration leave the session standalone.
5. Reconcile late evidence in either order and nest each verified launch under its Claude session and spawning lane in the Agent map, sidebar, and Bash card. A resumed Codex thread can have multiple launch edges over time. Give it one canonical details view and a reference at each verified launch, so provider totals and timeline rows count once. Preserve a direct Codex filter for browsing linked and standalone sessions together.
6. Provide the launcher convention and setup instructions in M1. The user updates fresh and resume instructions in <code>~/.claude/skills/codex-first/SKILL.md</code> and its launch references, and the <code>scripts/codex-resume</code> path where used. Keep one Claude-tracked background Bash command per worker, its prompt input, final <code>-o</code> report, logs, and actual exit status. Capture the verified Codex startup ID from the first <code>thread.started</code> event or native startup header before stderr is discarded or streams are redirected. Print the marker promptly to the tracked Bash task's stdout even if full output goes elsewhere. For resume, require confirmation of the expected thread in startup evidence and match the actual turn. A launch without provenance remains discoverable as standalone. Verify the marker end to end on the user's Git Bash workflow before M1 exit. [Codex non-interactive events](https://learn.chatgpt.com/docs/non-interactive-mode)

## Files view

| Evidence | File action and diff treatment |
| --- | --- |
| Claude <code>Read</code> with <code>input.file_path</code> and result | Requested read or Read according to result. Show range metadata and jump to the tool card. Failed reads keep their own state. |
| Claude <code>Edit</code> / <code>Write</code> with result | Pending edit/write before result, then applied or failed. Prefer <code>toolUseResult.structuredPatch</code> when it contains valid hunks. Use recorded old/new strings for a partial edit preview, or recorded full content for a known creation. An overwrite without a verified preimage is labeled accordingly. |
| Claude history snapshots and deltas | Associate a checkpoint with the recorded path and message. Keep separate from confirmed edit count and historical diff bases. Skip following backup file pointers. |
| Codex <code>FileChange</code> and <code>apply_patch</code> | Parse add/delete/update/move from <code>changes</code> or patch markers. Prefer the recorded outcome and affected paths. Capture an add/delete from recorded <code>content</code> or show a valid unified patch. |
| Claude Bash, Codex command records, and search calls | Use structured <code>parsed_cmd</code>, argv, named tool operations, or explicitly parseable output to attribute a path. Safe statically understood read/write commands can be shown as inferred when they succeed. Paths in a general command, search root, glob, or prose only count as references. Avoid guessing dynamic shell effects. |

Group by canonical path relative to the agent's recorded cwd. Preserve move relationships, repeated actions, first/last seen, lanes, result state, and provenance. Provide Read, Changed, Mentioned, and All filters, with provider and lane selectors. Separate reads, proposed changes, and applied changes in counts. From the row, jump to the source event or explicitly open the current local file if the path is permitted and exists. Show a recorded historical diff separately from current contents.

For inline diff, use the recorded hunks and stable line numbers with accessible added/removed labels. For fully reconstructed old and new text, register bounded read-only virtual documents and use <code>vscode.diff</code>. An unavailable preimage leaves a partial preview or a path-only entry. Never fill an old side using the current worktree. Package no Git shell evaluation, backup traversal, or workspace-wide file reading for this view. [VS Code extension API](https://code.visualstudio.com/api/references/vscode-api)
