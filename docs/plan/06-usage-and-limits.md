## Token fields and counting rules

| Provider and scope | Inputs | Derivation |
| --- | --- | --- |
| Claude per response | <code>assistant.message.id</code>, <code>message.model</code>, <code>message.usage.input_tokens</code>, <code>output_tokens</code>, <code>cache_read_input_tokens</code>, <code>cache_creation_input_tokens</code>, <code>cache_creation.ephemeral_1h_input_tokens</code>, <code>cache_creation.ephemeral_5m_input_tokens</code>, <code>output_tokens_details.thinking_tokens</code>, <code>service_tier</code>, <code>speed</code>, <code>server_tool_use.web_search_requests</code>, <code>server_tool_use.web_fetch_requests</code>. | Use recorded counts. Fresh input, cache reads, and cache writes are distinct input components. The two cache-write TTL fields break down the cache creation total. Thinking is a breakdown, so it is never added over reported output. Record tiers, speed, and tool counters separately when useful. |
| Claude subagent, root, model | Same response fields from the main and child transcripts. Use owning lane and source response identity. | Count a response once per provider scope even when multiple records carry usage for different blocks. Use <code>message.id</code> as primary identity and a validated provider <code>requestId</code> fallback when safe. Collapse replayed cross-lane copies only with affirmative identity and matching metadata. Sampled multiple-block duplicates shared usage. Take latest complete recorded counts for each response, not a sum of fragments. Roll up each distinct child response into its root and keep a main-only/children breakdown. |
| Codex per response/turn/thread | <code>token_usage_record.response_id</code>, <code>usage</code>, <code>turn_token_usage</code>, <code>thread_token_usage</code>, or fallback <code>event_msg/token_count.info.total_token_usage</code> and <code>last_token_usage</code>. The usage objects expose <code>input_tokens</code>, <code>cached_input_tokens</code>, <code>cache_write_input_tokens</code>, <code>output_tokens</code>, <code>reasoning_output_tokens</code>, and <code>total_tokens</code>. | Use exact response IDs and recorded model/turn for model and daily sums. Use latest cumulative snapshots only for their labeled scope. Cached input and reasoning output are breakdowns of the corresponding totals when the adapter verifies those semantics. Never add different cumulative scopes. Use fallback deltas only where successive snapshots within one scope are comparable and monotonic. A gap, reset, missing model or unverified descendant overlap marks a partial total. |
| Codex context fill | Last request <code>info.last_token_usage.input_tokens</code> and <code>info.model_context_window</code>. Fallback capacity from the active turn's recorded <code>model_context_window</code>. | Label an approximate last-request fill percentage using last-request input over its capacity. Never divide cumulative session tokens by context size. Show unavailable when either value or their shared request scope is missing. |
| Claude context fill | Status-line <code>context_window.used_percentage</code>, <code>context_window.context_window_size</code>, scoped to the reporting main session. | Prefer the official live gauge when the relay has a fresh value. Otherwise show last recorded request's input components and omit percentage when capacity is unknown. [Claude context window fields](https://code.claude.com/docs/en/statusline#context-window-fields) |

In the Codex sample, 6,538 <code>token_count</code> events included 6,462 non-null usage objects with capacity and 6,451 non-null rate-limit objects. Usage and limits can update independently. Never replace a known value with zero when input is unavailable. For Claude, label output as recorded or partial according to coverage. In M2, when the streamed assistant usage is provisional, prefer the explicit result token counts for their stated scope. Reconcile equivalent transcript and stream figures into one ledger entry. [Claude Agent SDK result fields](https://code.claude.com/docs/en/agent-sdk/typescript#sdkresultmessage)

Aggregate day and project from normalized response timestamps in the configured local timezone, preserving a separate unknown bucket for legacy data with insufficient attribution. Resume turns contribute to the day they ran. Include all discovered files eventually through bounded background backfill. Show scanning/incomplete coverage for charts before that finishes. Use one response ledger for session, descendant, profile, project, and date rollups. Render one summary per enabled adapter from its descriptor, plus a combined token total for the selected scope. A nested run contributes once through its canonical identity. Count observed local work independently of the provider's account quota across devices. Usage presents tokens, context fill, and limits only.

## Account quotas and status-line relay

**Codex.** In the observed <code>payload.rate_limits</code>, <code>limit_id</code> and <code>limit_name</code> can be null or strings. <code>primary</code> and <code>secondary</code> can be null or objects with <code>used_percent</code>, <code>window_minutes</code>, and <code>resets_at</code> in epoch seconds. Observed primary windows were 300 and 10,080 minutes, and the observed secondary window was 10,080 minutes. Label 5h and 7d from duration, independent of slot. Also observed nullable <code>credits</code> with <code>has_credits</code>, <code>unlimited</code>, and <code>balance</code>, nullable <code>plan_type</code>, and null <code>individual_limit</code>, <code>spend_control_reached</code>, and <code>rate_limit_reached_type</code>. M1 drops credit, balance, plan and unsupported values at normalization. It uses the latest valid observation per local profile namespace, <code>limit_id</code>/bucket, and duration, across eligible rollouts. Prefer an explicit Codex bucket. Keep other named buckets separate and accept null-bucket values for the main gauges only if their scope is independently verified. Display as a recent local account snapshot. If several accounts share a home, require user-scoped profiles or leave the account scope ambiguous.

**Claude on-demand refresh check.** Installed Claude Code 2.1.330 help exposes print and streamed JSON with no dedicated quota switch. Anthropic documents that a streamed <code>/usage</code> response can carry an experimental structured <code>usage_report</code> (SDK type available from v0.3.273). The current **Refresh limits** implementation invokes the single-command candidate <code>claude -p "/usage" --output-format stream-json --verbose</code> with isolation flags and parses the resulting usage text. The signed-in VS Code check moved from M1 to [M2 Phase E, item 5.5](m2-implementation.md#phase-e--keyboard-and-status-line). Use the installed native CLI in a disposable signed-in profile and trusted neutral cwd. Confirm it dispatches the built-in command and returns genuine account windows without starting a model turn. Record whether the installed CLI emits the structured event. If verified, project only the supported <code>usage_report.rate_limits.limits</code> window kinds, percent, and reset timestamp for that profile's refresh. Validate which kinds represent the account 5-hour and all-model weekly gauges, and keep narrower meters distinct. Handle absent meters independently and retain prior fresh relay data on refresh failure. Offer the relay and official Claude <code>/usage</code> when the command is unavailable. [Claude headless CLI](https://code.claude.com/docs/en/headless) · [Claude structured usage report](https://code.claude.com/docs/en/agent-sdk/typescript#sdkusagereport)

**Claude relay and one-click setup.** Show both Claude gauges by default in M1. On first run, ask once to **Enable Claude limits** for the selected Claude profile. On approval, Agent Lens installs its Windows-compatible relay and updates only the profile's user-level <code>statusLine</code> setting. Preserve unrelated settings and the prior status-line value. The relay passes original stdin and invocation context through to the existing command and preserves its visible output. With no prior command, use a minimal local status line. Make setup idempotent and honor effective managed or higher-precedence configuration. If chaining cannot be verified or the setting changes concurrently, surface the specific conflict and preserve the user's configuration. Provide **Uninstall relay** in Accounts or Usage. Restore the prior value or absence only if Agent Lens still owns the setting. Preserve subsequent user edits and clean up only Agent Lens artifacts. Remember a declined setup and expose the same action for later opt-in or additional profiles. [Claude status line on Windows](https://code.claude.com/docs/en/statusline#windows-configuration) · [Claude settings precedence](https://code.claude.com/docs/en/settings)

Claude sends the relay <code>rate_limits.five_hour</code> and <code>rate_limits.seven_day</code> when available, often after the first API response. Each window can be absent independently and its <code>resets_at</code> uses epoch seconds. Bind the relay to its profile, allowlist capture time, session ID for context attribution, numeric percentages/resets and context metrics, and atomically publish a small local snapshot. Use per-session snapshots or an equivalent concurrency-safe strategy and retain the newest valid sample per window. The extension reads only this projection. If setup is declined, a profile is unsupported, or a snapshot is stale, show the state, last observation time when available, and the applicable setup or refresh action. [Claude status-line data](https://code.claude.com/docs/en/statusline#available-data)

**Presentation and alerts.** The adapter declares its supported quota windows and emits normalized limit samples. The sidebar and status bar show 5h and 7d for each active Claude and Codex profile. The same gauges support other durations and skip adapters without limits. Usage detail shows profile, reset local time, relative time, reporting age, window identity and stale/missing reasons. Missing windows display a dash with an accessible explanation. An elapsed reset expires the snapshot until a new observation arrives. Trigger optional notifications for active profiles at configurable crossings, initially 80% and 95%, once per adapter/profile/account generation/bucket/window/reset/threshold. Deduplicate across VS Code windows when possible. Suppress historical or stale observations, avoid two alerts for a single jump through both thresholds, and include an Open usage action.

## Context fill levels

Context fill gets two warning levels on top of the percentage: **High** from 70% (amber) and **Critical** from 90% (red) by default. Both thresholds are user settings (<code>agentLens.context.warnPercent</code>, <code>agentLens.context.criticalPercent</code>), validated so warning stays below critical. Levels apply only where a percentage is shown: the Claude relay's <code>context_window.used_percentage</code> for its main session, and the approximate last-request Codex fill for its thread. A Claude subagent or any lane without a known capacity shows its recorded input tokens without a level. Codex levels are labeled approximate, the same as their percentage.

- **Where it shows.** The context gauge in the session header, the Usage detail summary, each Agent map card that has a percentage, and the sidebar session row when the level is High or Critical. The color always comes with a text label (High, Critical) and an accessible description, so the level never depends on color alone. Theme the colors through VS Code warning and error tokens.
- **When it updates.** Recompute on each new context sample for that scope. A stale or missing sample removes the level and shows the normal stale or unavailable state. A drop below the threshold, for example after compaction, clears the level right away.
- **Alerts.** An optional notification for crossing into High or Critical, off by default. Notify once per session, lane, level and compaction epoch. A jump straight past both thresholds gives one Critical alert. Suppress samples from historical discovery and deduplicate across VS Code windows where feasible, the same way as the quota alerts above. Context alerts and quota alerts stay separate, because one is about a single conversation and the other about the account.

Context levels are counted in the run statistics view (Later) as threshold crossings per session.
